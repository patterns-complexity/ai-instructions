# Compact Technology Rules

This is the complete concise form of `docs/technology`. Follow every mandatory statement; a statement that says **should** remains a strong recommendation. Do not add an abstraction, layer, file, or pattern unless these rules or the requested behavior require it.

## Precedence and scope

- Language-specific rules apply only to their language. If they conflict with architecture rules, use the architecture rule unless the language rule concerns performance or security.
- The repository is the project. Do not name the project after its main directory; use a fitting project name, or name a subproject for its domain concept.
- Keep implementation code in top-level `src/`. Split it into independently meaningful technical or domain modules, each named for the technical or domain responsibility it owns; modules may use different languages/build systems and may be independent or use explicit contracts. Keep repository-wide docs, build orchestration, and development tools outside `src/` when suitable.

## Architecture

- Each domain concept has one owning bounded context. Its owner owns its model, terms, invariants, persistence contracts, and use cases.
- Contexts must not import one another's internal domain, application, or infrastructure code, or read/write one another's persistence tables.
- Contexts communicate only through explicit public contracts, immutable DTOs, identifiers, commands, queries, or integration events.
- Share code only when it has no domain meaning and every consumer needs identical semantics. Never create domain packages named `shared`, `common`, `core`, `misc`, `helpers`, or `utils`.
- Each context has these logical layers: `domain`, `application`, `ports`, `infrastructure`, and `presentation`. Directory names may vary, but duties and dependency direction may not.
- `domain`: only aggregates/roots, entities, value objects, domain events/errors/policies/specifications, and stateless domain services. It imports no outer layer, database, framework, transport, serialization library, or vendor SDK.
- `application`: only commands, queries, use cases/handlers, transaction and authorization orchestration, and application results. It depends only on domain, ports, and published contracts. It contains no domain invariants, database queries, transport formatting, or concrete infrastructure construction.
- `ports`: interfaces for needed external capabilities (for example repositories, clocks, ID generators, gateways, event publishers, and file stores). Name the capability, never a technology: `PaymentAuthorizer`, not `StripeService`; `OrderRepository`, not `PostgresOrderRepositoryInterface`.
- `infrastructure`: concrete database/ORM, network, filesystem, broker, framework, and vendor adapters. It may depend inward; inner layers never depend on it.
- `presentation`: transport code such as HTTP controllers, CLI/RPC handlers, UI presenters, and request/response mapping. It may parse input, make one command/query, invoke one application entry point, and format the result; it contains no business rule or direct persistence access.
- Allowed dependencies: `presentation -> application`; `application -> domain|ports`; `infrastructure -> domain|ports`. All other cross-layer directions are forbidden. No cycles between files, packages, modules, layers, or contexts.
- Do not conceal dependency violations with lazy imports, reflection, service locators, global registries, or runtime lookup.
- The executable bootstrap is a composition root. It may import presentation, application, ports, and infrastructure only to construct and inject concrete dependencies. It must not make user-flow decisions, run application behavior, handle framework events, or format results.

## Domain and application design

- Each aggregate has one root. Repositories load/save only roots; other aggregates refer to roots by ID; internal entities are never persisted or mutated separately.
- Aggregate operations enforce all affected invariants before mutation and leave state unchanged on failure. Put objects together only when an invariant requires atomic change; do not load unbounded collections. Modify multiple aggregates in one transaction only for a documented atomic invariant.
- Entities have stable identity and compare by it. Domain fields are not publicly writable and have no setters; named domain operations validate every transition (for example `order.ship(shipment)`, never direct status assignment).
- Use immutable, self-validating, value-equal value objects for values with validation, units, constraints, or domain meaning. Do not reuse one primitive for distinct domain concepts.
- Domain events are immutable completed facts with past-tense names. They hold values and IDs only, never live entities, services, framework objects, or sessions. Explicitly map domain events to separate public integration events.
- Put behavior on its owning entity/value object. Use a stateless, I/O-free domain service only when no object owns the operation.
- An application handler performs one use case: load aggregates, call domain methods, save, and use external ports. Commands mutate; queries do not; no handler does both. Do not create `Manager`, `Helper`, `Processor`, `Engine`, or `Util` classes.
- Define one repository contract per aggregate root. Return roots, IDs, or explicit read projections only; use domain-language methods (such as `find_active_subscription_for_customer`), never generic repositories or methods such as `find(criteria)`, `get_all()`, or `save_any(object)`.
- Never expose ORM models, sessions, query builders, connections, or raw queries outside infrastructure.
- Use separate types for transport requests, commands/queries, domain objects, persistence records, transport responses, and integration events. Convert explicitly at boundaries. Domain objects have no database, JSON, HTTP, UI, or vendor annotations.

## Code structure and cleanliness

- One file has one primary concept and at most one class, including nested/private classes. A class file is named for that class and contains only its imports, class, and class-owned constants.
- Use separate files for each entity, value object, aggregate root, command, query, handler, event, error, DTO, repository contract/implementation, policy, specification, mapper, and controller. A function-only file exports at most one public operation; its private helpers serve only that operation. Generated, vendored, and framework-required migration files are the only exceptions.
- Handwritten production limits: 250 nonblank/noncomment lines per file; 150 per class; 40 per function; 5 parameters excluding receiver; nesting depth 3; cyclomatic complexity 10. Split by responsibility, never by arbitrary line count, statement compression, dynamic-dispatch concealment, or unrelated helper modules.
- An external callback/ABI function may exceed 5 parameters only when every parameter is required by its pinned declaration, no handwritten parameter was added, its other limits hold, and the integration boundary cites that declaration. This never permits ordinary APIs/helpers to exceed the limit.
- Group directories by feature, domain, component, or responsibility. Direct source-file counts: 0–10 normal; 11–15 allowed only when clearly related; 16–20 require review; >20 requires splitting unless strongly justified; >30 cannot receive another file before restructuring. Generated, migrations, vendored, and tool-controlled layouts are exempt.
- Split earlier when a clear subgroup, different change reason, repeated filename prefixes, mixed features, long scans, or a clearer name exists. Strongly prefer DDD/domain-named top-level directories over technical names, except tooling/config/non-domain code. Before adding a file, inspect the target directory; an existing messy directory, smaller diff, similar file, or import changes never justify worsening it. Do not replace one large file with many tiny files in one directory. Avoid catch-all directories unless all files have one clear responsibility.
- Constructors produce valid objects or fail; public methods preserve invariants; do not expose mutable internal collections. Model lifecycle with an explicit state type and named transitions, never contradictory booleans. Avoid boolean parameters; use separate methods, enums, or options.
- Dependencies are explicit constructor parameters. No global mutable state, service locator, or hidden singleton dependency.
- A function performs one operation at one abstraction level. Do not mix business decisions, persistence, transport parsing, external I/O, or response formatting. Prefer guard clauses; split names containing `and` unless it is one domain term. Constructors, getters/properties, equality, hashing, and string conversion do no external I/O. Do not mutate arguments unless documented in-place; no output parameters.
- Use canonical domain terms: one concept/one name and one name/one concept. Classes/values are nouns, operations verbs, collections plural, booleans begin `is|has|can|should|was`, and numeric names include unencoded units. Do not abbreviate domain terms or use vague names such as `data`, `info`, `item`, `thing`, `base`, `general`, `common`, `misc`, `helper`, or `manager`.
- Use distinct, condition-named error types. Never hide failure with null, empty values, or sentinels; never ignore an error. Catch only to recover, translate at a boundary, add material context, or perform required cleanup; do not log and rethrow the same error across layers.
- Create an abstraction only for two existing identical-semantic consumers, a side-effecting dependency needing a port, a context boundary contract, or multiple implementations. Do not abstract hypothetical reuse or merge merely syntactically similar code. A single-implementation interface is permitted only for a port or context contract.
- Comments state why, never what. Delete commented-out/unused code, types, methods, parameters, imports, and branches; no placeholder abstractions; TODOs require a concrete external work-item ID; do not use lint/type suppressions to hide design problems.

## Build, testing, performance, and parallelism

- Attempt a Dockerfile that builds from scratch when possible. If the required distribution/kernel has no usable image, create one when feasible and reasonable or disregard this requirement. Preserve built images for reuse if possible. Try to avoid rebuilding during code review; if repeat builds are unavoidable, consider caches or an artifact repository. If multi-stage Dockerfiles are possible and demonstrably reduce build time, use them. Consider a development Dockerfile for testing/debugging without full rebuilds, but first verify it is possible. Developers, not reviewers, change build files.
- Sandbox limits may justify requesting out-of-sandbox permission only when absolutely necessary; never assume a missing tool/library changes scope, because it may exist outside the sandbox.
- Performance is non-negotiable: code choices **should** prioritize ultimate performance at every opportunity. A better data structure, algorithm, or approach **should** be used when it improves performance; loops/recursion **should** be avoided when doing so improves performance. Library choice **should** follow performance, not popularity or familiarity.
- Safely parallelizable loops, recursion, and other computation **should** execute in parallel. Parallelism **should** improve when a better data structure/algorithm/approach permits it. GPU/accelerators **should** be used when transfer cost is lower than CPU execution; every GPU path requires a feature flag for CPU-only machines.
- Never bypass formatter, linter, or static-analysis rules inline. Raise and discuss a genuinely inapplicable rule instead.

## Documentation and acceptance

- Documentation describes version-controlled contracts, durable decisions, or reproducible requirements only; never base validity on a workstation, host OS, installed tools, caches, network state, or a transient reviewer environment.
- State environment requirements as reproducible capabilities (OS, architecture, ABI, toolchain, SDK, library baseline, device access), not one developer's machine.
- Do not use dates or relative time (`currently`, `now`, `today`, `as of`) as technical evidence. State present repository behavior and link its version-controlled manifest, configuration, implementation, or permanent contract.
- Historical dates may identify work but cannot establish validity. Before a spike observation supports a recommendation, convert it into reproducible prerequisites, validation commands, or acceptance criteria. Historical records are non-normative; permanent docs must restate accepted contracts, and historical evidence for an active compatibility claim must meet active documentation's reproducibility and version requirements.
- For a changing external tool/platform, pin the supported version/range, cite its authoritative versioned contract, and require revalidation when the pin changes. Before implementation, the exact pin may be deferred only when the needed capability is stated and pinning plus revalidation is an acceptance criterion. Never preserve an incidental local-tool result as project policy.
- Reject any implementation with: multiple concept owners; multiple classes/primary concepts per file; inward-to-outward imports; context-internal imports; business logic in controllers/repositories/persistence models; framework/vendor-aware domain code; writable entity state; bypassable aggregates; reused transport/persistence/domain type; generic repository, service locator, utility dump, or god class; dependency cycle; non-domain names; transient/date-relative documentation; or exceeded size/complexity limits.

## C++23 low-level rules

Baseline: WG21 N4950 (C++23); use C++ Core Guidelines for stated engineering practices. `MUST` means defined C++23 behavior/standard-library preconditions; `SHOULD` means strong Core-Guidelines practice.

- Typed operations require a live, suitably sized/aligned, initialized object; storage alone or a pointer cast is not an arbitrary object. A class object's lifetime ends when its destructor starts, its storage is released, or its storage is reused. Use real construction (`construct_at`/placement new) unless documented implicit-lifetime rules apply.
- `start_lifetime_as<T>` only starts a complete implicit-lifetime `T` in reachable, allocated, large-enough, aligned storage; it is not a constructor substitute.
- Before lifetime start/after lifetime end, a pointer is only a storage address: no member access, virtual dispatch, `dynamic_cast`, typed read/write, or other live-object operation. Cross-thread object publication requires synchronization after construction.
- Reused storage retargets old pointers/references/names only when transparent-replacement rules apply. Use `launder` only for a valid stale-pointer case; it cannot allocate, construct, align, start lifetime, or fix aliasing. Explicitly ending a nontrivial automatic/static/thread object's life requires a suitable replacement before its later implicit destruction. Never reconstruct an actually-`const` complete automatic/static/thread object in place.
- Never normally evaluate indeterminate values; narrow byte-like exceptions do not generalize. Initialize before typed use.
- Follow C++ type-accessibility rules; C effective-type folklore does not apply. `reinterpret_cast` grants no lifetime, alignment, accessibility, or valid representation. Inspect representation only via `char`, `unsigned char`, or `std::byte`; bytes do not automatically form a valid value.
- Byte-copy/restore guarantees apply to trivially copyable types only. Prefer `bit_cast` for equal-size trivially-copyable representation conversion, after proving the destination bits are valid. Do not treat padding/raw `sizeof(T)` bytes as portable equality, hash, serialization, network, or persistence data. Do not use unions for unrestricted type punning; only defined active-member/common-initial-sequence cases apply.
- Same address does not prove pointer-interconvertibility or object identity. Satisfy required alignment; `assume_aligned` promises existing alignment and `[[assume(expr)]]` promises a true reachable expression—false promises cause undefined behavior.
- Pointer arithmetic/subtraction stays within one array object (or its one-past position); a non-array object counts as a one-element array; subtraction needs a `ptrdiff_t`-representable result. One-past pointers are non-dereferenceable sentinels, not pointers to a neighboring object. Prefer spans, iterators, ranges, and containers where practical.
- Prevent signed overflow; unsigned wraps modulo 2^N. Reject zero or unrepresentable quotient division/remainder, invalid shift counts (negative or >= promoted-width), and out-of-range floating-to-integer conversion. Respect expression sequencing; no conflicting unsequenced scalar side effects.
- Match `new/delete` and `new[]/delete[]`, including custom allocator contracts. Polymorphic deletion requires the proper virtual destructor contract; do not delete incomplete types when complete destruction/deallocation semantics matter.
- Raw pointers/references **should normally** be non-owning. Use RAII; prefer scoped ownership when possible; use `unique_ptr` for transferred ownership and `shared_ptr` only for genuine shared ownership; avoid naked `new/delete` outside resource-management code. Destructors **should** not propagate exceptions. Mark a function `noexcept` only when all relevant paths uphold it.
- Data races are undefined. `relaxed` atomics provide atomicity, not unrelated-memory synchronization. Prove each acquire/release relationship through the specified atomic value/modification relation; modification order is per atomic object; fences are not generic memory flushes. `atomic_ref<T>` requires trivially-copyable `T`, required alignment, object lifetime through every reference, and valid competing-access discipline. Never use `volatile` for thread synchronization. Use custom lock-free code only when measured and proven for both C++ and hardware memory models.
- Do not rely on ordinary C++ layout, mangling, exceptions, STL types, or RTTI as a portable cross-compiler ABI; use a deliberate restricted ABI, usually C-compatible. Same bytes/address/`sizeof` never proves interoperability: prove lifetime, alignment, accessibility, representation, ABI, ownership, and calling convention.
- Clearly document which low-level assumption comes from ISO C++23, platform ABI, compiler extension/flag, or hardware guarantee; never treat extensions as ISO guarantees.
- Review order: lifetime; initialization; alignment; bounds; type accessibility; representation; ownership; construction/destruction; allocation pairing; sequencing; arithmetic; concurrency; memory ordering; optimizer promises; ABI.

## Rust low-level rules

Baseline: Rust Reference, standard-library developer guidance, Rustonomicon, and standard-library API contracts. `MUST` means soundness/documented Rust semantics; `SHOULD` means strong standard-library/compiler-team practice.

- `unsafe` never permits UB. It is sound only when no safe caller can cause UB. A safe API accepts every input its safe types allow; put unrepresentable caller obligations behind `unsafe fn`/trait or a validating constructor type.
- **Should** enable `#![deny(unsafe_op_in_unsafe_fn)]`. Keep every unsafe operation in an explicit `unsafe {}` block, including inside `unsafe fn`; each block **should** have a local `// SAFETY:` explanation. `# Safety` documents caller obligations, while `// SAFETY:` explains how the implementation met them.
- Create `&T`/`&mut T` only after non-nullness, alignment, dereferenceability, allocation size/lifetime, valid `T`, and aliasing requirements hold—even if never dereferenced. Use raw pointers, preferably `&raw const`/`&raw mut`, for uninitialized, under-aligned, temporarily invalid, aliasing-incompatible, or packed memory; never create an intermediate reference merely for a cast.
- Treat `&T`, `&mut T`, and `Box<T>` as optimizer-visible aliasing/ownership contracts. Mutate through a shared reference only using `UnsafeCell`; it does not allow aliasing mutable references or remove synchronization/data-race requirements.
- Prove pointer validity for each operation, including size, alignment, allocation/lifetime, provenance, initialization, and aliasing. Keep provenance with Strict Provenance APIs (`addr`, `with_addr`, `map_addr`); do not recreate arbitrary pointers from `usize`. Pointer arithmetic remains tied to its original allocation; equal numeric addresses do not prove validity.
- A typed value is valid as soon as Rust treats it as one. Use `MaybeUninit<T>` for uninitialized storage, and call `assume_init` only after initialization. Never generically `zeroed()` a `T`; zero requires a documented valid representation. Padding is not initialized payload: do not generically hash/compare/serialize raw `size_of::<T>()` bytes.
- `ManuallyDrop<T>` controls destruction, not initialization/validity; after manual drop, do not expose/use it as `T`. Treat `ptr::read` as a move: do not use/drop the source unless correctly replaced; handle returns, panics, and unwinding safely.
- Never rely on `repr(Rust)` layout for ABI/persistence; choose explicit `repr(C)` or `repr(transparent)` when required. `repr(packed)` does not permit unaligned references; use raw pointers and unaligned read/write. Prefer narrow conversions over `transmute`; use it only with a proven full representation relationship.
- Raw-pointer-owning generic types encode logical ownership/variance/drop checking/auto traits with correct `PhantomData` markers. Treat variance as safety design: incorrect pointer/marker variance must not permit invalid substitutions. `Pin` is a movement contract that unsafe construction/projection/destruction must preserve; unchecked extraction of `&mut T` does not remove that obligation.
- Every `unsafe impl Send`/`Sync` proves correct ownership, synchronization, aliasing, interior mutation, and generic bounds; never add it just to compile.
- Data races are UB. Base synchronization on Rust's memory model, not timing; `Relaxed` supplies only atomicity, and fences/atomics do not legalize conflicting non-atomic/raw accesses. Establish recognized happens-before relationships.
- Raw foreign APIs **should normally** remain behind an unsafe boundary. A safe FFI wrapper validates pointer/nullability, length, ownership, lifetime, alignment, initialization, thread safety, callbacks, and transfer before creating safe Rust values, and remains safe for every safe caller. ABI declarations must exactly match reality, including unwind rules and C-enum values/discriminants.
- `asm!` options, operands, registers, outputs, and clobbers are optimizer contracts and must be true. Force `#[inline(always)]` only with measurement/profiling evidence. Where Rust leaves aliasing, provenance, validity, or optimizer-sensitive behavior incompletely specified, use the conservative documented subset; never depend on current rustc/LLVM behavior.
- Review order: validity; lifetime; alignment; bounds; provenance; aliasing; initialization; ownership; drop; unwinding; concurrency; FFI/ABI; layout; unsafe boundary; compiler assumptions.
